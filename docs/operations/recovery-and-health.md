# 付款恢复、退款和运行健康

本功能属于 Polaris 面板；在线付款适配器位于配套 polaris-pro。两个配套 PR 应一起安排：先合并 Polaris（保留提交标题中的 `[skip release]`，跳过中间状态的自动发布），再合并 polaris-pro，最后手动触发 Polaris Release。两个仓库的新接口需要配套构建。启动时自动添加表，不修改旧订单权益。

## 付款和交付

易支付回调验证签名、商户、金额及订单后，先事务保存 `payment_receipts`。保存失败返回 HTTP 503 `fail`，让网关重试；保存成功返回 `success`。交付失败不会丢失收款记录：订单显示“已收款待交付”，后台每 10 秒扫描，每笔使用数据库租约避免多个实例同时处理。

Telegram Stars 的成功付款消息也先持久化。持久化失败时不推进 polling offset，下一轮重新获取。相同付款凭证只产生一次权益；同一订单的额外付款保留为人工对账项。USDT 延用链上扫描游标及事务发货，扫描失败保留游标，下次重试。

套餐被删除、权益快照损坏等永久错误进入人工处理。修复原因后，在订单列表点击“重试交付”（需要高权限确认）。重试只使用已存付款凭证；额外付款不能用该操作再次发货。带付款凭证的订单不能通过过期订单清理删除。

不同订单对同一用户的套餐续期、流量包叠加，以及管理员/API 用户变更，共用用户行锁。Telegram 首次开户另有买家锁，避免两个实例同时创建账号。

## Stars 退款

管理员申请后先保存退款任务，订单显示“退款处理中”。任务冻结原机器人凭据并加密保存，切换当前机器人不影响原订单的后续核验；API 不返回这些凭据。备份仍属于敏感数据，需要保护。

只有 Telegram 明确确认、返回明确的已退款错误，或退款流水/退款消息字段匹配时，才标记“已退款”。网络错误、响应丢失及其他 API 错误不会视为成功。结果不明时先核对原机器人的流水；完整扫描未找到退款才重试相同 charge ID。每次最多扫描约一万条流水；无法取得完整流水的任务持续等待并告警，需要人工检查原机器人权限/凭据和交易记录。

远端已确认而本地更新失败的任务保持 confirmed，下次只补齐本地状态。自动重试每 15 秒扫描到期任务。退款记录和付款记录保留，不自动删除。

## 集群升级与恢复

每个安装的数据目录新增 `cluster-instance-id`，重启保留，多个实例必须使用独立数据目录。升级操作先保存数据库请求和当前在线成员的投递记录；通知仅用于唤醒。每台实例每 5 秒读取自己的未受理操作，失败后 15 秒重试，24 小时到期后保留错误供排查。

恢复数据库和其他实例重载请求在同一事务提交，防止恢复成功但进程退出后通知丢失。运行中的操作、成员及健康状态不随业务备份导出或覆盖，避免恢复旧备份重放旧升级命令。

设置页显示受理进度和失败原因。“已受理”表示本地升级请求已写入或恢复重启已安排，**不代表升级成功**；成功/失败仍看原有升级结果通知和实例版本。旧版实例只能接收兼容通知，无法确认持久化操作，首次滚动升级期间可能仍显示未受理。Docker 实例继续使用镜像升级，无法通过宿主机升级组件受理。

## 健康状态和告警

设置 → 版本与更新新增运行健康：

- 收款后交付重试超过一分钟、需要人工对账的付款；
- 退款核验超过一分钟，集群请求超过一分钟未受理；
- USDT 扫描失败、流量结算失败/积压；
- Agent 队列写盘失败、超过 15 分钟积压、运行期间丢弃批次；
- 定时备份失败或超过预期时间未成功（每天 26 小时、每周 8 天）。

每分钟检查，使用现有 Telegram 管理员通知及 webhook 事件通道发出 `operational_alert`，同一实例的同一问题最多每 30 分钟提醒一次；配置共享 Redis 后跨实例共享去重，未配置时主实例切换可能再次提醒。需开启对应通知通道。告警发送仍依赖这些既有通道；通道自身故障时请在后台检查健康状态。

Agent 需要升级才能报告队列健康；旧 Agent 不上报时视为未知，不会凭空清除之前的故障。历史失败时间和最近成功时间保留；离线节点的记录可能是其最后一次上报，请结合节点在线状态判断。丢弃批次计数为本次进程运行累计，不能找回已经丢弃的流量。

管理员接口 `GET /api/v1/operational-health` 返回问题与最近成功/失败时间，`GET /api/v1/ready` 检查数据库连通性；二者位于配置的管理路径之下并要求认证。数据库不可用时认证本身也可能失败，健康探针应将所有非 2xx 视为未就绪。Redis 属于可回退组件，不作为数据库就绪的条件。
