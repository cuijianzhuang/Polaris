# 用户流量采集与来源排查

本说明对应 `fix/user-traffic-attribution`。代码审计和模拟计数器测试能确认风险路径，但没有生产节点的计数、批次及日志，不能据此确定某个用户异常用量的唯一原因。

## 从内核到用户的链路

1. 内核适配器 `CollectTraffic` 返回用户 ID 对应的上、下行增量。sing-box 的 v2ray stats 在本次修复前使用累计计数减去上次读数，修复后与 Xray 一样读取并清零；mihomo 使用连接 ID 的累计计数差。没有 v2ray stats 的 sing-box 仅提供标签流量，不能从标签总量推断单个用户。
2. Agent `collectFrom` 在多内核之间按用户汇总，排除限速绕行内部计数，以随机批次 ID、采集时间和序号（`epoch` + 递增 `seq`，与队列一起原子写盘）写入 `traffic-queue.json`。未确认批次会重试上报；普通断网不会因为没有实时使用就停止补报旧批次。上报时不持有队列锁，面板变慢不会卡住采集。
3. 面板 `ReportTraffic` 认证节点、检查用户归属、将负计数归零，在**一个数据库事务**里完成去重和入账：新 agent 按每个队列的已接受最大序号（`traffic_cursors`）去重，旧 agent（无序号）按批次 ID（`traffic_batch_seens`，保留 30 天）去重，流量累加进 `traffic_inboxes`。事务提交后才确认批次，所以已确认的批次不会丢，重发多少次、隔多久、面板是否重启或换了实例，都只计一次。标签计数单独存储，不作为用户扣量。
4. `settleTraffic` 先读出 `traffic_inboxes` 快照，在结算事务里按快照数额做条件扣减（`up >= ? AND down >= ?`）；某行已被其他实例结算则整个事务回滚，下一轮再算。结算失败时流量仍留在表里，不会丢也不会重复。然后将流量乘以结算时节点倍率，按方向四舍五入，再扣节点流量包，剩余部分扣账户。倍率后的流量进入小时和日统计；实际账户扣量进入用户 `UsedUp/UsedDown`。
5. 小时记录使用面板的**结算时间**，并非内核活动时间。上报带有 `CollectedAt`，但现有结算未按此字段拆分小时，因此离线补报可能使闲置时段出现流量。

## 已确认并修复的计数风险

sing-box 适配器原来在 `Start` 和 `Reload` 时无条件清空累计计数基线。但进程 `Start` 在已经运行时直接成功返回；SIGHUP 也只是异步发送信号，不能证明 stats 服务已经归零。若内核仍返回同一累计值，下次采集会把历史计数当成新流量。

现在 sing-box 的 v2ray stats 路径使用 `QueryStats(reset=true)`，与现有 Xray 采集一致，直接将内核返回值作为增量。上游 [sing-box v1.13.5 stats 实现](https://github.com/SagerNet/sing-box/blob/v1.13.5/experimental/v2rayapi/stats.go) 对每个计数器使用原子 `Swap(0)`，因此不再依赖 Agent 内存里的上次读数，也无需通过计数倒退猜测重载周期。Clash 标签统计路径保持连接差值方式，只在启动新进程前清空连接基线。

回归通过真实 gRPC 请求与模拟 stats 服务验证 reset 字段、服务名兼容回退、无新流量、存活进程的 Start / SIGHUP、正常增长、采集器重建。未使用真实 sing-box 二进制做端到端流量重放，仍需在测试节点验证所部署内核版本。

原子读取并清零需要由 Agent 独占该清零接口；其他工具同时清零会争抢计数。与 Xray 一样，内核完成清零但响应丢失、或 Agent 在落盘前崩溃，仍可能漏计。这次修复消除了内存基线重报路径，不等于端到端的恰好一次投递保证。

## 仍需结合现场证据排查的边界

- Agent 正常退出会先采集、上报，再停止内核；因此「Agent 重启必定让活着的内核重复上报」不成立。异常终止、残留进程和启动冲突需要另查服务管理配置与日志。
- 批次去重已持久化到数据库（见上文第 3 步），原来内存 / Redis 一小时去重导致的重复入账已消除。仍可能漏计的情况：内核计数已清零但 agent 在写盘前崩溃；agent 队列超过 50000 批（约 5 天离线）时丢弃最老批次。
- 活跃连接、客户端后台探测、同一订阅被别的设备使用，也可能产生真实的小流量。只有用户 ID、节点、结算小时不能证明具体是哪台设备或哪个域名；不展示推测结果。
- 倍率扩大、小额真实流量、历史离线补报、重复计数，需要通过来源数据与节点日志区分，不能只看账户已用量。

## 用户详情中的流量来源

「用户 → 编辑/详情 → 流量来源」支持最近 24 小时、7 天、30 天，按节点筛选并分页。显示每个结算小时、节点名称和 ID，以及：

| 字段 | 含义 |
| --- | --- |
| 原始流量 | Agent 上报并进入结算的字节增量，未乘节点倍率 |
| 倍率 | 实际结算倍率；同一小时多次结算且倍率变化时展示最小值至最大值 |
| 倍率后流量 | 倍率和取整后的统计量，等同既有小时流量口径 |
| 账户扣量 | 扣除节点流量包后，实际增加到账户已用量的字节数 |

这些字段与现有结算放在同一个事务里写入；失败回滚后重试不会仅重复来源数据。新字段由数据库自动迁移添加，不改写已有统计。小时数据沿用现有 90 天清理周期。

**历史数据不会伪造**：升级前只有倍率后流量，原始流量、历史倍率和实际账户扣量均展示「未记录」。升级发生在某小时中间，则该行展示「部分记录」，原始值和账户扣量仅覆盖升级后的结算；倍率后总量仍覆盖整个小时。合计遇到这类记录会说明不完整，不用当前倍率倒推过去。

账户重置、手动修改、每日/每月周期重置不会抹去小时历史，因此来源合计不一定等于当前账户已用量。删除节点后，保留其 ID，名称展示为未知节点。

查询接口：`GET /users/:id/traffic-sources?hours=24&node=<id>&limit=20&offset=0`。`hours` 最大 2160，`limit` 最大 200。管理员可访问；API 令牌需要 `traffic:read`，不返回 UUID、密码或订阅凭据；节点管理员无权访问用户级来源。

## 现场确认步骤

1. 在流量来源中定位增长的节点、结算小时，先比较原始流量、倍率后流量、账户扣量，确认是否只是倍率或流量包口径差异。
2. 检查同一时段 Agent / 面板是否升级、重启、断连或重载。若发生补报，结算小时不能当作实际使用小时。
3. 同时观察该节点内核同一用户的两次累计读数及进程启动时间，比较新增长的字节与面板原始流量。不要把节点网卡总流量当作单用户流量。
4. 若怀疑批次重试，保留批次 ID、采集时间、面板接收/结算时间和重试时间，确认是否同一批次多次入账。来源小时聚合不保留批次 ID，不能单独证明去重问题。
5. 若确认为真实后台连接，再结合在线设备/IP、客户端日志与凭据分发情况排查。不要先清零账户或删记录，以免丢失对账证据。
