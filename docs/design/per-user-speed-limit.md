# 设计：客户独立限速（Agent 限速转发）

状态：草案，待确认

## 1. 目标

- 每个用户可以设上行、下行速率（Mbps）。同一用户在一个节点上的所有连接（多设备、多入站、多内核）共用这份额度。
- 支持 Xray、sing-box、mihomo。Hysteria2 不支持，原因见第 7 节。
- 不限速的用户完全不经过限速器，没有任何额外开销。
- 改速率立即生效，不断线，也不重启内核。
- 不破坏现有功能：路由、分流、拦截规则、按用户的规则、链式出站、流量统计、端口限速（tc）都照常工作。

不在本期范围：
- 跨节点共享额度。每个节点各自限速，同一用户在两台节点上各得一份额度。
- 按目标网站分别限速。

## 2. 为什么不能直接让内核限速

官方 Xray、sing-box、mihomo 都没有按用户限速的功能。
- 现有的端口限速（`internal/agent/shaper.go`，tc）只能限制整个端口，同一端口上的所有人共用一份带宽。
- 入站流量是加密的（TLS / REALITY），Agent 在入口处看不出连接属于哪个用户。

唯一能区分用户的是内核自己，它解密后知道每条连接是谁的，三种内核都支持按用户路由：Xray 的 `user`、sing-box 的 `auth_user`、mihomo 的 `IN-USER`，代码在 `internal/core/*` 里已经在用。所以思路是：**让内核把受限用户的流量交给 Agent，Agent 限速后再交还内核。**

## 3. 方案：经 Agent 绕一圈

```
客户端 ──► 内核入站（识别出用户 u）
             │ 规则 0：user = u  →  出站 lim-u（SOCKS5，用户名 u）
             ▼
          Agent 限速器 127.0.0.1:Pl   ← 按用户 u 的令牌桶限速（上行 / 下行）
             │ 连回内核
             ▼
          内核回流入站 127.0.0.1:Pr（SOCKS5，账号 u#lim）
             │ 正常路由：拦截 / 分流 / 按用户规则 / 链式出站 / 直连
             ▼
          目标网站或下一跳
```

要点如下。
1. **只加一条规则**：每个受限用户一条，放在路由最前面，形如 `user:[u] + 公网入站 → lim-u`。回流入站不在条件里，流量回到内核后不会再被送回限速器。
2. **现有规则一条都不复制**：流量回流后走完整的原有路由，所以拦截、分流到美国节点、按用户的规则都照常生效。
3. **每个受限用户一个出站** `lim-u`（SOCKS5，用户名 = u）。限速器靠用户名认出是谁。
4. **回流入站的账号用 `u#lim`**。原因有两个：
   - 流量统计不会重复计算，采集时忽略 `#lim` 账号；
   - 面板生成按用户的规则时，把用户列表从 `[u]` 扩成 `[u, u#lim]`，这些规则在回流后仍然命中。
5. **TCP 和 UDP 都支持**：限速器实现 SOCKS5 的 CONNECT 和 UDP ASSOCIATE，所以 QUIC、游戏、语音这类 UDP 流量也会被限速。

### 为什么选这个方案，而不是另外两种

- **给每个受限用户复制一份全部规则**：规则数 = 规则数 × 用户数。Xray 每条 geosite 规则都会单独加载一份列表，用户一多内存就爆。
- **内核打 fwmark + tc / IFB**：开销最低，但依赖 iptables、IFB 内核模块，OpenVZ / LXC 等 VPS 上经常没有。下行方向只能在服务器入口间接限速，排查也难。可以以后作为可选的"高性能模式"再加。

## 4. Agent 限速器（新文件 `internal/agent/limiter.go`）

- 每个内核一个监听端口，只监听 127.0.0.1，端口由 Agent 分配（类似现在的 `apiListen`）。生成配置时把这个端口和回流入站端口一起写入内核配置。
- 认证：SOCKS5 用户名 = 用户 ID，密码 = 节点上随机生成的密钥。本机其他程序无法借用。
- 令牌桶用 `golang.org/x/time/rate`。
  - 每个用户一对桶（上行、下行），所有内核共用，因为同一用户可能同时连 Xray 和 sing-box 的入站。
  - 突发上限 = 1 秒的额度，最小 256 KB。
- 热更新：新配置到达时只改桶的速率，已建立的连接不断开。用户不再受限时，连接继续，但不再计速；新连接走规则 0 的变化。
- 观测：每个用户的当前速率和被限速的时长，随心跳上报，面板可以展示"谁正在顶满额度"。
- 安全：只接受到回流入站的转发，不会变成开放代理；单个用户的连接数设上限，防止耗尽文件描述符。

## 5. 各内核的配置改动

| 内核 | 规则 0 | 出站 `lim-u` | 回流入站 |
|---|---|---|---|
| Xray | `user` + `inboundTag` | `socks` 出站（带用户名、密码） | `socks` 入站，accounts 为 `u#lim` |
| sing-box | `auth_user` + `inbound` | `socks` 出站 `username` | `socks` 入站 `users` |
| mihomo | `AND,((IN-USER,u),(IN-NAME,…))` | `socks5` 代理 | `socks` 监听器 `users` |

- **增删受限用户**会改出站和规则。Xray 用已有的路由热更新（`internal/core/xray/hot.go`，`ado` / `rmo` + `adrules`），不重启；sing-box、mihomo 照现有方式重载。
- **只改速率**不改内核配置，只更新 Agent 里的令牌桶。
- **单用户 Shadowsocks**（mihomo）分不出用户，跳过并提示，与流量统计的现有限制一致。

## 6. 面板

- **数据模型**：
  - `store.User` 增加 `SpeedUpMbps`、`SpeedDownMbps`（0 = 跟随分组）；
  - `store.Group` 增加同名字段作为套餐默认值（0 = 不限）；
  - 有效速率 = 用户值，否则用分组值；用户属于多个分组时，取其中最高的。
- **下发**：`NodeSpec` 增加 `UserLimits []{User, UpKbps, DownKbps}`，只包含这个节点上能用的受限用户。
- **按用户的路由规则**：生成时把 `Users` 扩展出 `#lim` 别名（`internal/panel/spec.go`）。
- **流量统计**：采集时忽略 `#lim` 账号（`internal/agent` 的 collect 部分），避免重复计算。
- **界面**：
  - 用户表单、分组表单加"限速 上行 / 下行"；
  - 用户列表显示限速标签；
  - 节点页显示"正在被限速的用户"；
  - 用户中心 /u 显示自己的套餐速率；
  - 节点只有 Hysteria2 入站时，显示"Hysteria2 不支持独立限速"。

## 7. 限制与风险

- **Hysteria2 不支持**：它的路由（ACL）不能按用户匹配，也没有按用户的带宽控制。只能继续用端口限速，界面上会注明。
- **性能**：受限用户的流量在本机多走两次回环、多复制两次。估计在 1–2 核的 VPS 上，经过限速器的总吞吐能到约 1 Gbps，具体在原型阶段实测。不限速的用户不受影响。
- **待验证（原型第一步）**：Xray 的 SOCKS 入站账号能否作为路由里的 `user`、能否进入流量统计。若不能，Xray 的回流入站改用无 TLS 的 VLESS（客户端带 email），限速器多实现一个最简单的 VLESS 出站，其余设计不变。
- **限速是每节点独立的**：经链式出站转到美国节点的那部分流量，已经在香港节点限过速，美国节点上不再限。
- **延迟**：多一跳回环，增加约 0.1 ms，可以忽略。

## 8. 实施步骤

1. **原型与验证**（约 0.5 天）：用三种真实内核验证规则 0 + 回流 + 账号匹配，并测吞吐和 CPU。
2. **Agent 限速器**：SOCKS5 的 TCP / UDP、令牌桶、热更新、指标上报，附单元测试。
3. **三种内核的渲染**：生成规则 0、`lim-u` 出站、回流入站，Xray 支持热更新，流量采集忽略 `#lim`。
4. **面板**：数据模型、下发、规则别名、API、界面、多语言词条。
5. **端到端测试**（真实内核）：
   - 限速 10 Mbps 的用户实测约 10 Mbps，不限速的用户不受影响；
   - 拦截规则、分流到其他出站、按用户的规则仍然生效；
   - 流量不重复计算；
   - 修改速率后不断线、立即生效。
