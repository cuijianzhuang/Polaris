# 公开状态页（服务状态）

> 状态：设计稿，待审定（D1–D11 为推荐方案，用户可逐条改）。四项 flyx 借鉴中的第 2 项（第 1 项见 [backhaul-monitor.md](backhaul-monitor.md)，其 D10 已为本项预留 `carriers` 字段与开关，本设计直接消费）。
>
> 先交代调研结论：Polaris **已经有一块公开页**——探针监控的公开版（`/status` + `/status/data`，默认关，见 [probe-monitor.md](probe-monitor.md)），但它本质是「服务器监控大盘的匿名版」：CPU / 内存 / 磁盘 / 负载 / 流量 / 价格一应俱全，面向站长自查。flyx 的状态页是另一种东西：面向客户的「服务是否可用」页——只回答哪些地区、哪些节点在线，延迟如何，可用率多少，不暴露运维细节。本设计在现有公开面之上补这一层，不另起第二块公开页。

## 1. 目标与非目标

### 目标

- 客户打开一个链接即可看到：整体服务状态、每个公开节点的在线状态 / 地区 / 延迟 / 三网（就绪时）、近 7 / 30 天可用率，以及数据截至时间。
- 隐私口径严于现有监控页：独立白名单投影，IP、端口、协议、版本、资源、用户数据一律不出（见 D5）。
- 复用现有公开面基建：`status_page` 开关、`statusGate` + decoy、快照缓存、`uitheme` 主题、订阅域名白名单，不新建第二套公开面机制。
- 消费第 1 项 D10 定死的 `carriers` 字段形状与 `probe_public_carriers` 开关，不另议接口。

### 非目标（首版刻意不做）

- 不替换、不下线现有监控公开视图（它服务站长自查与既有分享链接）。
- 不做事件 / 维护公告系统：故障时间线、维护排期是另一个量级的功能；公告沿用现有 `status_note` 一条文本。
- 不做半公开口令模式（见 D11）。
- 不新增匿名按节点查询接口：整页只有一个快照端点，防枚举。

## 2. 现状与复用点

| 基建 | 位置 | 本设计如何用 |
| --- | --- | --- |
| 公开状态页（监控版） | `internal/panel/statuspage.go`：`statusGate`（关时走 decoy）、`statusSnapshot`（1 秒缓存 + 构建互斥合并）、`statusTitle` / `status_note`；`internal/panel/router.go` 在 `/status` 与 `/status/data` 注册（与 admin path 冲突时不注册） | 服务视图挂同一页、同一 gate；服务快照仿 `statusSnapshot` 的缓存形态另建 |
| 监控快照组装 | `internal/panel/probe.go` 的 `probeOverview(public bool)`：public 分支排除 `revoked` 与 `status_hidden` 节点、隐藏 Address / Version / 进程与连接数，流量受 `status_show_traffic`、价格与到期受 `status_show_cost` 门控 | 服务投影的数据源头与它同源（延迟、心跳新鲜度口径一致），但序列化走独立白名单结构体（D5），不复用 `probeNode` |
| 延迟数据 | `latencySummaryForNodes` → `latencyNow{Ms, Avg, Loss, At, Spark, SparkLoss}`（按目标维度）；源数据 `store.NodeLatency` 为 5 分钟槽，保留 7 天（`probe.go` 的 `latencyKeep`） | 服务页只取精简投影（每目标 ms / 近 1 小时 loss），不下发 spark 明细 |
| 心跳 / 资源槽 | `store.NodeMetric` 5 分钟槽（`internal/panel/statsreport.go` 的 `recordMetric`，心跳落槽写入），保留 30 天（`internal/panel/server.go` 的 prune） | 可用率的唯一数据源（D6）：槽存在即该 5 分钟有心跳 |
| 节点字段 | `store.Node`：`Name` / `Region` / `Flag`（ISO 国旗码）/ `SortOrder` / `StatusHidden`（字段注释即 "left off the public status page"）/ `OwnerID` / `DisplayName` / `ReviewState` | 范围过滤与分组现成；展示名口径见 D4 |
| 开关与设置 | settings 键 `status_page`（默认 false）/ `status_title` / `status_note` / `status_show_traffic` / `status_show_cost`，白名单在 `internal/panel/api_misc.go`；管理入口在探针大盘页 `web/src/pages/Probe.tsx` 的公开状态页卡 | 沿用 `status_page` 总开关，不新增第二套开关位；新增设置见 §10 |
| 主题 | `internal/uitheme`（`assets/tokens.css`，经 `uiTokens` 注入公开页模板）+ `internal/panel/probe_assets/monitor.css` 的 `--pv-*` 变量；公开页模板已支持明暗双色与手动切换；favicon 走 `siteIcon` | 服务视图直接复用，不新增主题设置（D8） |
| 域名 | `internal/panel/subhost.go` 的 `subOnlyPath` 已把 `/status` 与 `/status/data` 列入订阅域名可服务路径；门户在 `portalPath`（`/u`），公开地址由 `portal_public_url` 决定 | 服务端点须同步加入 `subOnlyPath`（D2）；门户入口见 D11 |
| 限流器 | `sharedLimiter`（`internal/panel/sharedstate.go`，集群共享计数，sub / shop / mailcode / ticket / haJoin 已在用，`Allow(key)` 形态） | 给新服务快照端点加一档（D10），与既有档位同机制 |

硬约束（调研确认）：

- **现有公开监控快照未按 `OwnerID` / `ReviewState` 过滤**：`probeOverview` 只排除 revoked 与 hidden，用户自带节点（内部名 `un-<id>`、`DisplayName` 为所有者自取）会与管理员节点混排出现在公开监控页。这是既成事实；服务视图必须定新口径（D3），监控视图是否同步收紧列入未决。
- `/status/data` 当前**无限流**，防护只靠 1 秒快照缓存与构建互斥；响应头 `Cache-Control: no-store`，CDN 不缓存。
- **可用率无现成口径**：全仓没有 availability 计算；可用数据源只有 `NodeMetric` 槽存在性（30 天）与 `NodeLatency` 槽（7 天），且两者口径不同、不可混用（D6）。
- `carriers` 依赖第 1 项批 3 落地（在 `probeOverview` 上扩展）；未落地前服务快照恒无此字段，页面须优雅降级（D7）。
- 同步升级纪律：新列只增不删（`public_name` 为 additive 列）；公开页是服务端模板 + 内嵌 JS（`probe_assets/status.js`），不进 React 构建链。

## 3. 定位与入口

### D1 定位：演进现有 `/status`，一页双视图，不新建第二块公开页

`/status` 页新增「服务状态」视图并设为默认视图；现有监控内容降为同页的「详细监控」视图（视图切换，锚点 `#monitor` 可直达）。理由：公开面收敛——一套开关、一套 gate、一处分享链接、一个标题与公告；若另开一块页，两块页必然在开关、主题、节点范围上分叉，隐私口径迟早不一致。代价：`status.js` 与页模板要重排，监控视图老用户的默认落点变化（以视图切换 + 锚点缓解）。

### D2 入口与开关：沿用 `/status` 与 `status_page`，新增服务快照端点与「仅服务」开关

- 路径沿用 `/status`：面板域名与订阅域名均可达（现状），新端点 `GET /status/service` 同步加入 `subOnlyPath` 白名单。不做自定义路径：可预测路径利于分享、CDN 规则与白名单维护；与 admin path 冲突时不注册的现有保护不变。
- 总开关沿用 `status_page`（默认关），服务视图不另设开关位。
- 新增设置 `status_service_only`（默认 false）：开启时只公开服务视图，监控视图与 `/status/data` 一并走 decoy。理由：愿意给客户看可用性、但不愿公开 CPU / 价格的站长是真实存在的姿态差异，只用一个总开关逼他们二选一会让服务视图也开不出来。代价：多一个设置与一组 gate 分支，批 1 测试需覆盖两形态。

## 4. 节点范围、粒度与别名

### D3 节点范围：服务视图默认只含管理员节点；粒度按节点、按地区分组呈现

- 范围：`revoked = false`、`status_hidden` 非 true、`OwnerID = ""`（管理员节点）。用户自带节点默认**不进**服务视图——它们是其他用户的机器，其名称与在线状态不属于站长的服务承诺，挂进客户状态页等于替别人背书可用性。
- 备选（不做）：给用户节点加「所有者自愿公开」位——涉及所有者同意流与门户入口，量级独立，列未决。
- 粒度：按节点逐个列出，页面按 `Region` 分组展示（分组是前端呈现，数据仍是节点数组）；分组头显示该组在线比（如 2/3 在线）。不做「只按地区聚合」模式：客户排障要看到具体节点，纯聚合会把单点故障藏进平均数里。

### D4 公开别名：新增节点列 `public_name`，快照只输出最终展示名

- 新增 `nodes.public_name`（additive，可空），节点编辑表单加「公开名称」一项。
- 展示名口径：`public_name` 非空用之；否则用管理员节点的 `Name`。服务端快照只输出这一个最终展示名，不下发原始 `Name`，更不下发 `DisplayName` / `OwnerID`。
- 理由：真实节点名常是主机名 / 供应商编号（如机房内部命名），站长需要一个对外说法；内部名牵连订阅生成与运维脚本，不能为了公开页去改内部名。代价：别名要逐节点维护，没填的回退内部名，隐私收益随维护度打折（见 §12）。

## 5. 服务快照与字段白名单

### D5 白名单投影：独立结构体正向白名单，禁止「复用 `probeNode` 再删字段」

新端点 `GET /status/service` 用独立结构体序列化。现有监控快照是「同结构、public 时少填几个字段」的黑名单做法——`probeNode` 每加一个字段都会默认带进公开面；服务快照必须反过来：新字段默认不带，逐项评审后才进白名单。

快照顶层：`{title, note, at, stale, summary:{total, online, state}, nodes:[...]}`。每节点白名单：

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `name` | D4 最终展示名 | 不下发节点 ID，行标识即展示名 |
| `region` / `flag` | `Node.Region` / `Node.Flag` | 分组与国旗 |
| `state` | `Node.Status` + 心跳新鲜度归并 | 只出三态：`online` / `degraded` / `offline`（口径见下） |
| `latency` | `latencyNow` 精简投影 | 每目标只留 `{name, carrier, ms, loss}`（loss 为近 1 小时口径），不给 spark 明细（监控视图已有） |
| `carriers` | 第 1 项 D10 | 仅 `probe_public_carriers = true` 时出现，形状 `{ct, cu, cm: {ms, loss, line}}` 原样透传（D7） |
| `uptime7d` / `uptime30d` | `NodeMetric` 槽聚合（批 2） | 百分比，一位小数；数据不足为 `null` |
| `uptimeDays` | 同上（批 2） | 近 30 天每日可用率数组，前端画条 |

三态口径：`online` = 节点状态为在线类且心跳新鲜（≤ 90 秒，与 `probeOverview` 的 `TelemetryFresh` 同口径）；`degraded` = 心跳新鲜但任一目标近 1 小时失败率 ≥ 50%，或状态为在线类但心跳已过期；`offline` = 其余。三态之外不发明更多状态词。

**禁止清单**（服务端以断言测试钉住，逐项不得出现在服务快照中）：`Address`、`PublicIPv4` / `PublicIPv6`（含现有监控页给出的「有无 IPv4 / IPv6」布尔——服务页一并收紧）、入站与端口、协议与传输细节、内核与 Agent 版本、OS / Arch / Cores、CPU / 内存 / 磁盘 / 负载 / 系统 uptime、流量与额度、价格与到期、节点 ID、`OwnerID` 与任何用户数据、探针目标地址（只给目标名与运营商，沿用现有口径）。

## 6. 可用率

### D6 做：7 / 30 天双窗口，心跳槽口径，零新表

- 定义：可用率 = 窗口内有 `NodeMetric` 槽的 5 分钟数 / 窗口应有槽数。分母起点取窗口起点与节点 `CreatedAt` 的较晚者；节点在窗口内删除即不在页面（沿用节点集合口径）。
- 数据不足：节点建成不足 24 小时，或窗口内应有槽 < 12（1 小时）时输出 `null`，页面显示「数据不足」——不显示 0%，也不显示 100%。
- 口径声明（页面脚注必须写明，不允许后续迭代悄悄去掉）：可用率按面板观测到的 Agent 心跳计算；面板自身停机期间全站计为不可用；5 分钟粒度，短于 5 分钟的中断可能不体现。
- 不用 `NodeLatency` 算可用率：那是「节点到测速目标」的可达性，与节点可用是两回事，混用会把测速目标故障算成节点故障。延迟失败率只作 `latency.loss` 与 degraded 判定，不进可用率。
- 存储：零新表。`NodeMetric` 保留 30 天恰好覆盖长窗口；聚合在服务快照构建时按 `node_id` + 按日计数完成（节点量级 ≤ 数百，走主键前缀，30 秒快照缓存吸收重复计算）。90 天窗口需要日聚合表，本项不做（列未决）。

## 7. 三网字段接入

### D7 直接消费第 1 项 D10：字段名、形状、开关全部沿用，不另议

- 字段名 `carriers`、形状 `{ct: {ms, loss, line}, cu: {...}, cm: {...}}`、开关 `probe_public_carriers`（默认 false）全部按 [backhaul-monitor.md](backhaul-monitor.md) §7 定稿；开关关闭时服务快照不出现该字段（与监控快照的字节级口径一致）。
- 服务快照构建时与 `/status/data` 共用同一 `carriers` 组装结果（实现上抽共用函数，禁止两处各算一份、口径漂移）。
- 呈现：节点行内三网小段——电信 / 联通 / 移动各给 ms 与线路标签（`line`），失败率高时标色；`carriers` 缺失（开关关或第 1 项未落地）时整段不渲染，不留空占位。
- 依赖：本项批 2 的 carriers 部分依赖第 1 项批 3；若第 1 项未落地，批 2 只交可用率，carriers 透传随第 1 项落地后以增量 PR 接入——字段与开关已定，不阻塞本项主体。

## 8. 主题与品牌

### D8 首版只复用现有主题与品牌设置，不做 flyx 式独立配色

- 复用：`uitheme` tokens + `monitor.css` 的 `--pv-*` 变量、明暗双色（跟随系统 + 手动切换，公开页模板已有）、标题 `status_title`（回退逻辑沿用现有 `statusTitle`：`site_title` + 后缀）、公告 `status_note`、favicon 走现有 `siteIcon`。
- 不做：独立主色 / 背景 / Logo 上传等自定义主题设置。理由：双套主题变量必然漂移，且现有 `--pv-*` 刚完成中性灰定版（见 [probe-monitor.md](probe-monitor.md)）；flyx 的可换主题是它的产品选择，不是状态页的必要条件。代价：白标需求强的站长只能改标题、公告与站点图标，不能改主色。
- 留口：若后续要做，只需把 `--pv-cyan` 一个强调色变量映射到设置项即可，不需要重构——批 3 时评估，不在本设计承诺。

## 9. 刷新、呈现与总体状态

### D9 服务视图 30 秒轮询，明示数据截至时间；总体横幅三档由节点状态归并

- 服务视图轮询 30 秒（与快照 TTL 对齐）；监控视图维持现有节奏，两视图互不影响。移动端与隐藏标签页沿用现有页的暂停轮询口径。
- 页面明示「数据截至 HH:MM:SS · 每 30 秒更新」；快照带 `at`，页面以 `at` + 浏览器单调时钟推进（沿用 [probe-monitor.md](probe-monitor.md) 既有口径，避免访客本机时钟偏差）；`at` 距今超过 2 分钟时顶部出现「数据可能已过期」提示。
- 总体横幅三档：全部节点 `online` → 「全部服务正常」；`offline` + `degraded` 占比 ≤ 1/3 → 「部分服务异常」；> 1/3 → 「大面积服务异常」。横幅只由节点状态归并，不引入人工状态覆盖（人工说明用 `status_note` 公告）。

## 10. 性能与防护

### D10 独立缓存 + 限流 + stale 降级；公开面只留一个快照端点

- 缓存：服务快照独立缓存槽与构建锁，TTL 30 秒，构建互斥合并（仿 `statusSnapshot` 的双重检查形态），不与监控快照互相阻塞。
- 响应头：服务快照给 `Cache-Control: public, max-age=15`，允许订阅域名前的 CDN 短缓存（30 秒轮询下命中率可观）；HTML 与监控快照维持 `no-store` 不变。
- 限流：给 `/status/service` 加一档 `sharedLimiter`（建议 120 次 / 分钟 / IP：正常轮询每标签页只用 2 次，留足多标签页与 CDN 回源余量；超限 429）。这是状态类端点第一次限流，档位与 sub / shop 同机制、集群共享计数。
- 降级：构建失败时返回上次成功快照并置 `stale: true`（状态页最坏也要给出最后已知状态与其时间戳）；从未成功构建过时返回 503，文案沿用现有口径。
- 枚举防护：服务面只有整页快照一个端点，不新增按节点 / 按地区查询参数；节点不下发 ID，别名不做 slug 路由——没有可枚举的东西。

## 11. 与门户的关系

### D11 门户只加入口，不做分层数据；半公开口令不做

- 入口：`status_page` 开启时，门户导航（`sub.PortalNavigation`，由服务端按有效开关供给链接）加「服务状态」一项指向 `/status`。同域相对路径即可：订阅域名的 `subOnlyPath` 已放行 `/status`，门户独立域名（`portal_public_url`）同样由面板服务、路径可达。
- 不做分层可见性：登录与否看到同一份公开快照，不给登录用户加字段——分层会逼出第二套白名单与测试面；登录用户查自己节点的既有面是用户中心节点状态（`portalNodeStatus`），不经公开页。
- 半公开口令不做：口令进链接必然外泄，且与 decoy 的「不存在」语义冲突；有此需求的站长用反代层 Basic Auth 解决，产品不背。

## 12. 接口与设置汇总

| 接口 / 设置 | 变化 |
| --- | --- |
| `GET /status` | 模板扩展为双视图（服务默认 / 监控），共用 `statusGate` |

## 14. 风险与未决

- **两视图节点范围不一致**：服务页按 D3 收紧后，用户会问「为什么监控页有、服务页没有」。现有监控页未排除用户自带节点、且显示其内部名——监控页是否同步收紧（至少对用户节点改显 `DisplayName`、排除未审核节点）**需用户拍板**；它改变既有公开行为，本设计不擅自带改。
- **可用率口径的公信力**：面板停机计入节点不可用对站长不利，但这是唯一不撒谎的口径——面板观测不到的时段不能假装在线。脚注声明是产品口径的一部分。若用户接受不了，备选是只展示近 7 天并标注采样口径，不用 30 天背书（D6 相应收紧）。
- **别名维护成本**：`public_name` 要逐节点填，没填的回退内部名，上线初期多数节点仍显示内部名，D4 的隐私收益打折；是否需要批量设置入口，批 1 后看反馈再定。
- **未决**：①监控页节点范围是否同步收紧（见上，本项最需要拍板的一条）；②90 天可用率（需日聚合表）是否值得做；③用户自带节点的「所有者自愿公开」是否立项；④`status_service_only` 是否真有必要，还是批 1 直接让服务视图成为唯一公开默认（取决于监控公开页的实际使用情况）。

## 15. 决策清单

| 编号 | 问题 | 推荐 | 备选与代价 |
| --- | --- | --- | --- |
| D1 | 与现有公开监控页的关系 | 演进 `/status` 为双视图（服务默认 / 监控次级），不新建第二块公开页 | 新建独立页：两套开关 / 主题 / 范围口径必然分叉，隐私口径迟早不一致 |
| D2 | 入口、路径与开关 | 沿用 `/status` + `status_page` 总开关，新增 `/status/service` 端点与 `status_service_only`（默认关） | 自定义路径：分享、CDN 与白名单维护成本全涨；只用总开关：想公开可用性又不愿公开资源的站长被迫二选一 |
| D3 | 节点范围与粒度 | 只含管理员节点（排除 revoked / hidden / 用户自带），按节点列出、按地区分组 | 纳入用户节点：替他人机器背书可用性；只按地区聚合：单点故障被平均数藏起来 |
| D4 | 节点展示名 | 新增 `public_name` 别名列，快照只输出最终展示名 | 直接用内部名：主机名 / 供应商编号对外暴露；改内部名迁就公开页：牵连订阅与运维脚本 |
| D5 | 字段控制方式 | 独立结构体正向白名单 + 禁止清单断言测试 | 沿用监控快照的黑名单减字段：`probeNode` 每加一字段即默认进公开面，迟早漏 |
| D6 | 可用率 | 做：7 / 30 天、心跳槽（`NodeMetric`）口径、零新表、脚注声明面板停机计入 | 不做：状态页只剩瞬时状态，客户无从判断长期质量；用延迟槽算：把测速目标故障算成节点故障；90 天：需新日聚合表 |
| D7 | 三网字段 | 直接消费第 1 项 D10 的 `carriers` 形状与开关，共用组装函数 | 本项另定形状：第 1 项批 3 已定稿，另议即返工与双口径 |
| D8 | 主题与品牌 | 只复用现有 tokens / 标题 / 公告 / 图标，不做独立配色设置 | flyx 式自定义主题：双套变量漂移，白标收益不抵维护；完全不留口：后续加主色要动模板结构 |
| D9 | 刷新与总体状态 | 30 秒轮询 + 明示数据截至 + 超期提示；横幅三档由节点状态归并 | 沿用监控的 2 秒节奏：可用性页没有这个实时性需求，白耗构建与流量；人工状态覆盖：与公告重复，多一个误设面 |
| D10 | 性能与防护 | 独立 30 秒缓存 + CDN 短缓存头 + `sharedLimiter` 限流 + stale 降级 | 照搬监控端点现状（1 秒缓存、无限流、失败 503）：被刷时构建压力大，状态页在最需要时反而空白 |
| D11 | 门户与分层 | 门户只加「服务状态」入口，登录不加字段；半公开口令不做 | 分层可见性：第二套白名单与测试面；口令模式：链接必外泄，与 decoy 语义冲突 |
