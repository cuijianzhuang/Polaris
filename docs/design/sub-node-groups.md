# 设计：订阅节点组加工（呈现组）

状态：设计稿，待审定（D1–D7）。借鉴 flyx 的「节点组」与 Sub-Store 风格订阅管理：统一挑选、过滤、去重、改名，落地直连与中转线路独立勾选，订阅按组折叠呈现、标签、置顶、克隆与批量管理。本稿只定义管理员呈现层与加工层，不改变授权与计费口径。

## 1. 目标与非目标

目标：

- 管理员能把「一类节点在订阅里长什么样」沉淀成可复用的组：选哪些（谓词）、怎么加工（过滤/改名/去重/排序）、以什么形态出现（直连/中转）、在客户端里归到哪个分组。
- 同一套组能被套餐和组合订阅复用，改一处、处处生效，且有预览、有版本意识，不静默改变已交付订阅的语义。
- 未启用本功能时，所有订阅输出与现版本逐字节一致。

非目标：

- 不做新的授权维度。加工层只能在用户已授权的节点集合里做减法，永远不能把未授权入站「加工」进订阅。
- 不做跨面板节点组共享，不做用户间组市场。
- 首版不做 JS 脚本加工（D4）。

## 2. 现状（调研结论，含代码位置）

### 2.1 订阅渲染管线

- 面板用户订阅：`internal/panel/subscription.go` 的 `subscription()`（`GET /sub/{token}`）做账号状态、到期、额度、设备校验后，调 `subNodesForTrace` 展开节点：`store.GrantsSQL`（`internal/store/models.go`）一条 UNION 查出全部授权入站，节点配额过滤后由 `buildSubPrefetch`（`internal/panel/sub_prefetch.go`，常数级查询批量预取）补齐 endpoints、chains、cores 等，逐入站展开为 `sub.Node`。随后可选地跑一条**全局算子链**（设置 `sub_apply_ops_users` + `globalOperators()`，`internal/panel/subrender.go`），最后 `serveNodes` 按格式分发渲染。
- 渲染器在 `internal/sub/`：`clash.go`、`singbox.go`、`surge.go`、`loon.go`、`links.go`（分享链接/Base64）、`scheme_render.go`。Clash 的 proxy-groups 来自规则方案（Scheme）的 `Resolve`，是**策略分组**（节点选择/自动测速/规则指向），不是节点集合分组；两层概念不要混。
- 组合订阅（订阅转换页）：`store.SubProfile`（`internal/store/models.go`）= 来源 `SourceIDs` + 可选 `PanelUserID` + 本地 `Operators` + `ProcessingGroups` 引用 + 每格式模板；拉取、组合与执行链在 polaris-pro，公共仓提供模型、界面与 `internal/sub` 算子。
- 性能特征：`/sub/{token}` 无服务端渲染缓存，每次请求全量展开 + 渲染，靠 `subLimit` 限流；展开侧靠 prefetch 保持常数级查询（历史上订阅渲染做过 N+1 优化）。加工层的新代码禁止在节点循环内查库，见 D7。

### 2.2 已有的算子与处理组（不要重做）

- 算子已存在：`internal/sub/ops.go` 的 `ApplyChain` 支持 `filter`（协议、地区、名称 include/exclude 正则、丢弃信息节点）、`rename`（正则替换 + 模板，变量含 `{flag} {region} {regionZh} {protocol} {name} {index}` 等）、`sort`（region/protocol/name/server + 自定义地区序）、`dedup`（按连接身份去重），链尾恒做一次 `Dedupe`。
- 可复用处理组已完成：`store.SubProcessingGroup` / `SubProcessingGroupVersion`，见 [可复用订阅处理组](sub-processing-groups.md)：有序引用、跟随最新/固定版本、变更影响预览（ETag + `expectedRevision`）、引用删除保护、备份恢复。但它目前**只被 SubProfile 引用**，面板用户订阅只有一条全局链，没有按套餐/用户分层的加工。

### 2.3 已有的「组」概念盘点（新概念必须避让）

| 既有概念 | 职责 | 与本设计的关系 |
| --- | --- | --- |
| `store.Group`（含 `Plan=true` 的套餐） | **授权组**：经 `GroupInbound` / `GroupNode` / 节点 Level 决定用户能用哪些入站，并承载套餐属性（流量、天数、重置、限速、设备数） | 是呈现组的上游：先有授权集合，才谈呈现。禁止把呈现字段塞进 Group，改呈现误触权限的风险不可接受 |
| `store.UserAccess` | 用户直绑节点/入站，授权的补充路径 | 同上，只决定集合 |
| `store.SubProcessingGroup` | 可复用的**加工步骤**集合（版本化） | 呈现组的加工链直接引用它，不另造规则载体 |
| 节点 `sort_order`、入站 `Tag`、节点 `Flag/Region` | 排序与分类的原始信号 | 呈现组谓词与排序的输入 |
| 规则方案 Scheme | 客户端策略分组与规则 | 呈现分组与之分层共存，见 D5 |

### 2.4 落地直连与中转在数据模型里的表达

展开层已经把形态分开：`store.Endpoint.Kind` 区分直连/CDN/中转（`relay`），中转端点绑定 `RelayChainID`；`store.Chain`（`Mode=proxy`、首跳为该入站、至少两跳）生成中转端点。`Inbound.RelayOnly` 与落地核心自动接受 PROXY 的入站**根本不产出直连端点**——这是内核约束，不是呈现偏好。展开后的 `sub.Node` 带有 `PanelKind`、`PanelChainID`、`Region`、`TrafficRate`（倍率）、`Source` 等元数据，呈现层按形态过滤不需要回查数据库。

### 2.5 用户侧与管理员批量现状

- 用户对自己订阅能做的：选 CDN 运营商/地区与优选池（`User.CDNCarrier/CDNRegion/CDNPreferred/CDNPool`）、门户预览与绑定（`internal/panel/account_binding.go`）、重置令牌。不能改名、隐藏、排序或自选子集。
- 管理员批量已存在：`bulkUsers`（`internal/panel/api_users.go`）支持 create / delete / delete-depleted / enable / disable / reset-traffic / extend / set-limits / add-group / plan。缺的是**标签**：`store.User` 无标签字段，列表筛选维度只有状态/套餐/分组。
- 到期预警只有单档：`internal/panel/renew_reminders.go` + `User.WarnedFor` 记录已提醒的到期日，无 30/7/1 天分级。
- `SubProfile` 无标签、置顶、排序字段，无克隆接口（现有路由见 `internal/panel/router.go` 的 `/sub-profiles` 一组）。

### 2.6 脚本加工的可行性边界

代码库没有任何 JS/表达式沙箱先例：`go.mod` 无 goja、otto、expr、cel 等依赖；`internal/plugin` 只有 manifest 定义，订阅 transform 的执行不在公共仓。声明式算子已覆盖 Sub-Store 的主流用法（按地区/协议/关键字过滤、正则改名、模板命名、去重、排序、丢弃信息节点）；缺口主要是按倍率/形态过滤（可扩展算子字段解决，见 D2）和任意逻辑（按延迟动态筛选、复杂条件命名）。

## 3. D1 核心概念：呈现组（订阅视图组），两层分离

**推荐**：新增独立概念「订阅视图组」（下称视图组），定义为三元组：

1. **选择谓词**：在已授权节点集合上的声明式条件（地区/协议/节点名/入站 Tag/形态/中转链/倍率），只做减法；
2. **加工链**：引用 `SubProcessingGroup`（可多个、有序、跟随/固定版本，语义与 SubProfile 完全一致）+ 本组本地算子，执行顺序沿用既有口径：全局链 → 被引处理组 → 本地算子；
3. **呈现属性**：组名、图标（emoji/文本）、排序权重、是否在客户端单独成组（D5）。

绑定关系分两层：

- **管理员层（首版）**：视图组序列绑定到套餐（`Group.Plan=true`）与 `SubProfile`。用户订阅的最终节点 = 授权集合依次过各视图组（组内取谓词命中子集加工，组间按绑定顺序拼接，跨组同连接去重保留先出现者）；未命中任何视图组的节点进「默认组」原样输出，保证启用前后集合不丢节点。
- **用户层（后续批，见分批）**：用户个人覆盖只能在管理员给定的视图组集合内隐藏整组或组内节点、调整个人顺序，不新造谓词、不改名。

不选的备选：

- 给 `store.Group` 加呈现字段：权限与呈现耦合，改个名字要走授权变更的审计与回滚，得不偿失。
- 每用户物化一份节点清单：节点上下线、链变更都要逐用户维护，数据量与失效面都失控；谓词式定义天然跟随现状。

数据模型（全部 additive，新表 + JSON 列，不改既有表语义）：

- `SubViewGroup`：`ID / Name（唯一）/ Remark / Selector JSON（谓词）/ ProcessingGroups JSON[[]SubProcessingRef] / Operators JSON[[]sub.Operator] / Kinds JSON（形态勾选，见 D3）/ ChainIDs JSON / Icon / SortOrder / Pinned / Enabled / Revision / CreatedAt / UpdatedAt`。谓词与算子 JSON 上限沿用处理组口径（规则 JSON ≤ 48 KiB、算子 ≤ 64 步）。
- 绑定不新建关联表：套餐侧在 `Group` 加 JSON 列 `ViewGroups []string`（有序的视图组 ID 列表）；`SubProfile` 加同名列。用户个人覆盖留到后续批再定表（`UserViewPref`），首版不预埋。
- 视图组被绑定时禁止删除（与处理组的引用删除保护同口径）；停用视图组 = 该组节点回落默认组，不报错、不丢节点。
- 版本口径：视图组首版只做 `Revision` 递增 + 审计，不做处理组那样的不可变版本表；谓词/算子变更的影响面是呈现而非授权，风险等级低一档。后续若要固定版本引用再补版本表（未决问题 2）。

命名说明：不用「节点组」作实体名——flyx 的 node group 同时管授权与呈现，Polaris 的授权已有 Group 体系，实体改叫视图组，界面文案可用「订阅分组（视图组）」降低理解成本。

## 4. D2 加工管线：首版算子增量，不动既有四算子语义

在 `internal/sub/ops.go` 增量扩展（全部向后兼容，旧 JSON 解析结果不变）：

- `filter` 增加：`kinds`（direct / cdn / relay，按 `Node.PanelKind`）、`chainIds`（按 `Node.PanelChainID` 白名单）、`maxRate`（倍率上限，按 `Node.TrafficRate`，覆盖 flyx 的倍率过滤场景）、`tags`（入站 Tag，需展开层把 `Inbound.Tag` 带进 `sub.Node`——目前模板变量里已有 `{tag}`，节点结构需补字段，属展开层小改）。
- `rename` 模板变量补 `{kind}`（直连/中转）、`{chain}`（中转链名）、`{group}`（当前视图组名，供 Base64 等无分组格式拼前缀）。
- `sort` 增加 `rate` 键（按倍率）。
- `dedup` 不改：键仍是连接身份；同入站的直连与中转端点连接不同、不会误删，同入站多 CDN 端点口径保持现状。视图组拼接后的跨组去重沿用 `ApplyChain` 尾部 `Dedupe`。
- 视图组的选择谓词复用 `filter` 的字段集（同一套结构、同一校验），不另发明谓词语言；谓词本质是「只保留」型 filter。

管线顺序固定为：展开 → 全局链（现状）→ 按绑定顺序逐视图组（谓词 → 处理组链 → 本地算子）→ 跨组拼接去重 → 渲染。视图组之间不共享中间结果，每组都从全局链输出的全集取子集——语义简单、可预览、组顺序只影响拼接次序与去重优先。

## 5. D3 直连与中转独立勾选：组定义期声明，渲染期过滤

**推荐**：视图组用 `Kinds` + `ChainIDs` 声明形态：如「香港组只要中转」「日本组直连+中转都要」就是两个视图组各自的勾选。渲染期在谓词一步按 `PanelKind/PanelChainID` 过滤，不在定义期物化任何节点/端点清单——节点新增中转链后自动出现在勾了 relay 的组里，链删除自动消失。

与既有强制规则的叠加关系写死：呈现过滤只能减不能增。`RelayOnly` 与 autoProxy 入站在展开层不产出直连端点，视图组勾了 direct 也变不出来；反之管理员想让某入站「只走中转呈现」用视图组即可，不必改入站属性（那会影响全部用户，视图组只影响绑定的套餐/订阅）。

L4 转发（`store.ForwardRule`，realm/GOST 端口转发）不在订阅节点展开范围内，与本设计的「中转」无关，不纳入勾选维度。

## 6. D4 JS 脚本：首版不做，声明式先行

**推荐**：首版与第二批都不引入 JS。理由：

- 无沙箱先例，引入 goja 类引擎等于在面板进程内执行管理员脚本：死循环/内存膨胀直接拖垮面板（订阅是高频公开接口），必须配超时、内存上限与并发隔离，工程量不亚于一个独立功能；
- 脚本要加工节点就必须看到节点**完整凭据**（UUID/密码/PSK），脚本的存储、备份导出、审计都随之变成凭据面，处理组现有「规则 JSON 不含凭据」的安全性质会被打破；
- D2 扩展后，声明式对 Sub-Store 常用场景的覆盖已足够，剩余长尾（按实时延迟筛节点等）本身依赖运行时数据，未必适合放在渲染期脚本里。

后续若要做，前置条件（缺一不可，须用户单独拍板）：脚本运行在独立子进程或 wazero 沙箱、单次执行硬超时（建议 ≤ 50 ms）与输出节点数上限、脚本内容按凭据级敏感数据管理（加密存储、不进普通备份明文）、失败时整链报错不静默跳过（与处理组现有口径一致）。另一条备选路径是走已有插件 transform 扩展点把脚本需求放到核心之外，本设计不展开。

## 7. D5 订阅呈现：分组映射与标签/置顶/排序的归属

- **有分组能力的格式**：视图组（`Grouped=true`）映射为一个客户端分组——Clash 为 `select` 型 proxy-group（组名 = 视图组名，可带图标前缀），并把这些分组按视图组顺序注入方案主 `select` 组的首位，其余策略分组（url-test 等）仍由 Scheme 决定，节点同时出现在策略组与视图组里是允许的（Clash 本就支持一个节点多组引用）；sing-box 映射为 `selector` outbound 并挂到主 selector 下；Surge/Loon 映射为同名 select proxy-group。
- **无分组能力的格式**（分享链接/Base64）：按视图组顺序拼接节点，`{group}` 模板变量供管理员决定要不要拼组名前缀；默认不拼，保持与现状观感一致。
- **默认组**：未命中任何视图组的节点在分组格式里落入「默认」组（名称可配，默认用站点名或「全部节点」），保证分组视图下集合完整。
- **兼容红线**：用户未绑定任何视图组时，全部格式输出与现版本逐字节一致（回归测试以固定夹具断言）。深度定制 Scheme 的用户开启视图组后，视图分组只做「追加」，不改写 Scheme 既有分组与规则指向（冲突优先级见未决问题 4）。
- **标签/置顶/拖拽排序的归属**：都落在**管理员侧**——视图组与 SubProfile 列表支持标签（`Tags` JSON 数组）、置顶（`Pinned`）、拖拽排序（写 `SortOrder`）。用户侧首版只读：门户订阅页按管理员编排呈现，不提供个人改序，避免个人顺序与管理员编排、客户端缓存三方不一致。到期分级预警属用户管理侧，见 D6。

## 8. D6 批量管理：补标签与分级预警，不重做 bulkUsers

- **用户批量**：`bulkUsers` 已覆盖启停/续期（extend）/重置流量/改限额/加组/换套餐。本设计只补两件：
  1. `store.User` 加 `Tags`（JSON 字符串数组，additive），用户列表支持按标签筛选，`bulkUsers` 增加 `tag` / `untag` 动作；标签即轻量分组，不新建实体。
  2. 到期分级预警：`renew_reminders.go` 从单档扩展为多档（默认关，可配如 30/7/1 天），`User.WarnedFor` 改为按「到期日 + 档位」记录已发档位（JSON 列 additive），避免同档重复打扰；沿用现有通知渠道与模板（`remindtpl.go`）。
- **订阅/视图组批量**：SubProfile 与视图组列表支持按标签筛选、批量启停；新增一键克隆：`POST /sub-profiles/:id/clone` 与 `POST /sub-view-groups/:id/clone`，复制定义与引用关系，名称加后缀、令牌重新生成（SubProfile）、不复制统计数据。**不做**跨组批量改算子（无预览的批量改规则风险过高；改规则走处理组的影响预览流程）。
- flyx 的「批量续期/重置流量」对象是用户订阅，在 Polaris 即用户批量，已有，不重复建设（见 2.5）。

## 9. D7 性能与缓存：展开常数查询不回退，加工只做内存计算

- 加工全程是对 `[]sub.Node` 的内存变换，复杂度 O(节点数 × 算子数)；正则在链加载/保存时预编译并缓存（保存时 `ValidateChain` 已做编译校验，执行期复用编译结果，禁止每请求 `regexp.Compile`）。
- 视图组定义（谓词 + 链）按 `Revision` 在内存缓存解析结果，绑定关系随套餐/Profile 读取（已有查询内），**禁止在节点循环内查库**；展开路径的查询数以 `sub_prefetch.go` 现有常数级为基线，新增查询只允许按「每请求常数次」出现（视图组定义一次批量读入）。
- 上限沿用既有口径：每套餐/Profile 绑定视图组 ≤ 10 个，每组算子 ≤ 64 步、规则 JSON ≤ 48 KiB，单订阅节点数沿用来源上限 5000 的量级约束。
- 渲染结果缓存（按 用户 + 授权/视图组 revision 的短 TTL 或 ETag）**不进首批**：到期、额度、配额都是实时语义，先量化（见验收）再决定，避免缓存把「刚到期仍能拉订阅」这类问题引进来。

## 10. 分批计划

### 批 1：视图组模型 + 算子增量 + 用户订阅接入（管理员层）

- `SubViewGroup` 模型与 CRUD（管理员会话、审计、删除引用保护）、`Group.ViewGroups` 与谓词/filter 扩展（kinds/maxRate/tags、rename 新变量、sort rate 键）。
- 用户订阅管线接入：套餐绑定视图组后按 D1/D2 顺序加工；未绑定用户输出逐字节不变。
- 管理界面最小版：视图组列表/编辑（谓词表单 + 算子编辑复用处理组组件）、套餐编辑里挂视图组序列。
- 验收：固定夹具回归（未绑定 = 基线逐字节一致）；绑定后过滤/改名/去重/倍率过滤生效且集合不丢节点（未命中进默认组）；订阅展开查询数与基线一致（查询计数断言）、既有订阅基准耗时不劣化（同机同数据 p95 对比，劣化 > 10% 视为不通过）。

### 批 2：直连/中转勾选 + 分组呈现 + 影响预览

- `Kinds/ChainIDs` 勾选落地（含按链选择）、D5 分组映射（Clash/sing-box/Surge/Loon + Base64 拼接序）、视图组变更影响预览（仿处理组预览：列出受影响套餐/Profile 与用户数，改定义需带预览 ETag 确认）。
- 验收：同一入站在不同视图组以直连/中转形态独立出现/隐藏；`RelayOnly` 入站无法被勾出直连（负向用例）；四种分组格式的客户端导入冒烟（以现有渲染回归夹具扩展断言分组结构）。

### 批 3：管理补齐 + 用户标签与分级预警

- SubProfile/视图组标签、置顶、拖拽排序、一键克隆；用户 `Tags` + 列表筛选 + `bulkUsers` tag/untag；到期多档预警。
- 验收：克隆产物与源定义一致（除名称/令牌/统计）；批量打标签可筛选可回滚（untag）；同档预警不重复发送（多档各发一次）。

### 批 4（可选，单独审定）：用户个人覆盖与脚本评估

- 用户个人视图覆盖（在管理员视图组内隐藏/个人排序，门户订阅页生效）与 D4 前置条件满足后的 JS 沙箱方案单独立项。本批不默认排期。

## 11. 未决问题（需用户拍板）

1. **许可分工**：处理组的执行链在 polaris-pro、模型与界面在公共仓；但用户订阅的算子执行（全局链）本来就在公共仓。视图组在用户订阅侧的执行放公共仓还是沿处理组口径归 Pro？这决定社区版能否用视图组（建议：模型与用户订阅侧执行放公共仓，SubProfile 侧引用沿用 Pro 口径——但与「处理组 Pro 专属」的现有边界不完全一致，需拍板）。
2. **视图组版本化程度**：首版只做 Revision + 审计，不做不可变版本表与固定版本引用（D1）。若管理员需要「某套餐锁定旧版视图组」，需补版本表，成本约等于复制处理组版本机制。
3. **命名与入口**：实体叫「订阅视图组」，管理入口放订阅转换页（与处理组并列）还是用户/套餐页（与绑定方并列）？建议前者为主入口、套餐编辑里只做引用选择。
4. **与深度定制 Scheme 的优先级**：视图分组注入主 select 首位对已有定制方案是侵入性的；是否提供「仅追加到末尾」或「不注入主组、只独立成组」的绑定选项？
5. **JS 脚本的风险接受度**（D4）：若用户坚持要脚本加工，需先确认凭据可见面与子进程隔离的成本，再单独立项。
