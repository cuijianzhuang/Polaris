# 入站一键中转与转发

参考 [FLYX 中转文档](https://kure29.github.io/flyx/guide/relay) 的“围绕落地入站创建线路”思路：选择已有入站和中转节点，由面板分配端口、生成配对配置、发布中转入口并统一清理。本轮提供后端接口，现有页面布局不变。

## 能力与边界

| 模式 | 配置 | 行为 |
| --- | --- | --- |
| 原样转发 | `mode: l4` | realm 转发，按照落地协议保留 TCP / UDP；不建立代理账号，不改变原协议 |
| 认证隧道 | `mode: tunnel`，`transport: tcp` 或 `ws` | GOST 成对配置接收端和发送端，自动生成认证信息；UDP 可经隧道承载 |

一条线路支持 1–3 个中转节点，最后接到已有落地入站。节点不能重复；落地入站必须已启用且面向用户。原样转发要求落地监听地址可被上游访问；隧道可接到仅本机监听的入站。要求接收 PROXY protocol 的入站暂不支持一键配置，应使用现有手工转发功能匹配发送端。

TCP / WS 隧道提供认证和转发，**不会额外添加 TLS 加密**；客户端原有协议及加密保持不变。一键配置暂不包含 TLS / WSS / QUIC 隧道、来源白名单或 PROXY protocol 自动配置。现有手工配置功能保留。

```text
客户端 → 中转 A 公网入口
           → 中转 B 认证接收端 → B 本机转发端
                                  → 落地认证接收端 → 原入站
```

中间节点的本机转发端只监听 127.0.0.1，不自动开放公网防火墙；接收端固定目标，不能由客户端指定任意目的地址。认证信息加密存储，不通过管理接口返回，只随节点私有配置下发。

## 接口流程

下列路径相对于面板 `APIBase`（默认 `/api/v1`；自定义管理路径时为该路径加 `/api/v1`），使用管理员登录返回的 Bearer token。节点受限操作员和现有 API 令牌暂未开放这些新接口。

| 方法与路径 | 用途 |
| --- | --- |
| `POST /inbounds/:id/relays/preview` | 预览，不创建资源 |
| `POST /inbounds/:id/relays` | 应用已预览方案 |
| `GET /inbounds/:id/relays` | 查看受管线路及每个节点的下发状态 |
| `PUT /inbounds/:id/relays/:rid/state` | 启用 / 停用，正文 `{"enabled": true}` 或 `false` |
| `DELETE /inbounds/:id/relays/:rid` | 删除线路及其受管入口 |
| `PUT /inbounds/:id/publication` | 设置发布策略，正文 `{"relayOnly": true}` 或 `false` |
| `POST /inbounds/:id/relays/:rid/diagnose` | 手动分层诊断，无需正文 |

预览请求示例：

```json
{
  "name": "香港中转 → 新加坡落地",
  "mode": "tunnel",
  "transport": "ws",
  "relays": [
    {"nodeId": "香港节点ID", "port": 24001},
    {"nodeId": "中间节点ID"}
  ],
  "remark": "业务线路"
}
```

`relays` 按连接顺序填写，不包含落地节点，落地由 URL 中的入站确定。`port` 可省略，由面板在 20000–60000 中选择；中间隧道接收端口也自动分配，必要时可用 `tunnelPort` 指定。首个中转没有隧道接收端，不填 `tunnelPort`。落地接收端口由面板分配。

预览返回 `planToken`、`expiresAt`、`chain`、入口 `address` / `port`、`network`、`ports` 和 `warnings`。`ports` 列出节点、端口、网络、引擎及是否需要公网放行，供检查云安全组。离线节点和禁用自动防火墙的节点会提示警告；预览不能保证远端离线机器上的端口空闲。

检查后，原样提交返回的令牌：

```json
{"planToken": "预览返回的完整值"}
```

方案有效期 10 分钟，绑定创建预览的管理员、目标入站和节点地址。首次应用前会重新检查端口和输入；占用端口、过期方案、节点地址或入站配置变化均需重新预览，不会静默换用别的端口。应用不要求再次提供隧道密码。

同一个方案重复提交只创建一次，也支持 `Idempotency-Key` 请求头。创建、入口关联、审计及重放记录在同一事务中提交；失败整体回滚。SQLite 写事务和 PostgreSQL 事务 advisory lock 协调一键创建。尚未部署到 Agent 的旧版本不能识别新隧道配置，应先升级参与线路的 Agent。

## 订阅与生命周期

- 创建时生成该入站的中转入口。默认发布策略下，若此前依赖默认直连发布，会保留为显式直连入口；已有直连 / CDN / 中转入口保持原有集合。创建线路不会自动切换发布策略。
- 如果原先已明确只发布中转入口，停用或故障时不会擅自新增直连入口。客户端已有订阅缓存需刷新。
- 停用线路会从期望节点配置和新订阅中移除该线路；启用时重新生成配置。
- 删除线路、落地入站或线路中某个节点时，清理该线路及所属入口，对剩余节点重新下发。手工转发、直连和 CDN 入口不随线路删除。
- 受管线路不能经旧的通用链路更新接口修改，也不能单独删除其入口；换路径时应重新预览创建，再删除旧线路。

### 仅通过中转提供

将 `relayOnly` 设为 `true` 后，用户订阅与分享链接只展开该入站的有效中转入口，过滤直连与 CDN 入口。存量默认 `false`，保持升级前行为。修改入站和创建入站也可显式传入 `relayOnly`；旧编辑器未传此字段时保留原值。导出、导入和克隆保留该策略；克隆不会复制旧线路，应为新入站另建线路。

这个开关不要求已经存在可用中转。没有中转、线路停用、删除最后一条中转或其入口时，保持不发布直连；离线也不自动退回直连。原始直连 / CDN 入口记录保留，关闭此策略后按原有记录发布，不会额外新建入口。打开策略后新建一键中转也不补建隐式直连入口。

此策略控制订阅和分享，不修改入站监听、防火墙或客户端已有的订阅缓存；TLS SNI、REALITY 目标和线路名称仍保留协议所需信息。需要限制实际直连访问时，还应配置来源白名单或仅本机监听等网络限制。仅中转提供的入站不再执行原先的直接健康探测，避免把有意关闭直连误报为故障，改用线路诊断。

## 状态与诊断

创建成功只表示事务已保存。查询返回各节点的 `desiredRev`、`appliedRev`、`requiredRev` 和错误，汇总为 `pending`、`syncing`、`applied`、`offline` 或 `failed`。入站被关闭时为 `blocked`，线路被关闭时为 `disabled`。关闭状态表示期望配置；具体移除仍需等待 Agent 应用，不能当作立即断开所有现有连接。

`applied` 表示 Agent 已应用所需配置，不能替代真实业务连通性验证。现有 `POST /chains/:id/probe` 对中转逐跳检查 TCP 目标端口，隧道检查接收端口，并保留落地 HTTP 探测；它不是完整隧道认证、代理登录或 UDP 端到端测试。部署后还应使用真实订阅验证协议、上下行和 UDP。

### 分层诊断

`POST /inbounds/:id/relays/:rid/diagnose` 返回 `deployment`、`network`、`checkedAt`、`checks` 和汇总 `state`。它使用管理后台的管理员权限，节点受限操作员和现有 API 令牌暂未开放。每项检查包含 `kind`、`state`、来源节点、目标、延迟和说明：

| `kind` | 检查范围 |
| --- | --- |
| `deployment` | 各节点配置已应用；停用、离线、应用错误或等待下发时返回 `not_ready` 并跳过网络检查 |
| `entry_tcp` / `entry_tls_handshake` | 面板到用户线路入口的 TCP 连接；TLS / REALITY 入站还尝试 TLS 协商，延迟包含解析、连接及握手。不校验证书，也不验证 REALITY 或代理凭据 |
| `hop_tcp` | 上一跳 Agent 到下一跳监听端口；隧道使用接收端口。不能证明隧道认证正确 |
| `landing_egress_http` | 落地 Agent 自身到固定 HTTP 测试地址的出口，不经过中转或用户代理入站 |
| `proxy_business` | 当前为 `not_tested`，明确未测试代理登录、上下行、UDP 端到端业务 |

即使所有可执行检查通过，汇总也为 `partial`，`businessVerified` 保持 `false`；发现网络失败时为 `failed`，不会将“入口端口打开”误标成完整业务通过。UDP 入站跳过入口 TCP / TLS 检查；原样 UDP 转发跳过逐跳 TCP 检查；UDP 经 TCP / WS 隧道时可以检查隧道接收端的 TCP 端口，仍不能据此声称 UDP 可用。

诊断的网络检查支持请求取消并共用 15 秒超时，结果即时返回，不修改入站告警或落地路由健康，也不使用、创建用户凭据。旧链路定时探测同样对原样 UDP 返回 `skipped: true`，不再因对应 TCP 端口关闭把落地节点判为故障，此时仍以心跳状态判断节点在线。

## 参考截图的功能映射

截图中的“隧道”是可复用配置，“规则”负责具体的监听与目标。本轮继续以受管线路为资源边界，避免同时引入第二套互相覆盖的转发规则。现有手工多目标转发仍可独立使用。

入口多选与多跳必须分开表达：选择入口 A、B 表示两条独立线路 `A → 落地`、`B → 落地`；当前 `relays: [A, B]` 明确表示一条串联线路 `A → B → 落地`，不能作为多入口接口使用。未来批量创建应单独提供入口集合字段及逐入口预览、应用结果，不能改变已发布接口的含义。共享隧道还需显式引用计数、凭据轮换与删除保护，当前各线路的隧道认证独立。

快速入站模板、监测点 / 运营商探测已有对应功能，后续可复用这些能力。获取真实客户端 IP 需成对配置 PROXY protocol 并验证内核支持；来源白名单需处理动态 IP、IPv6、防火墙实现及回滚，这两项暂不自动开启。

## 验证与后续方向

测试覆盖预览无写入、重复提交、端口冲突、过期 / 失效方案、事务回滚、停用及订阅行为、资源清理和多实例重放。真实 GOST 测试使用本地三进程验证 TCP / WS 双跳的 TCP、UDP 转发，以及错误密码被拒绝。

下一步值得继续借鉴的是：使用专用诊断身份完成代理业务验证、多入口批量编排、来源白名单与匹配的 PROXY protocol 配置，以及带证书校验的 TLS / WSS 隧道。后续页面可以调用这些接口提供一键配置，当前不改 UI。
