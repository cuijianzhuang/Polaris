# 运维通知策略

> 管理界面入口现已补齐，见[界面接入说明](operations-ui.md)；文中“仅后端/API”是首版交付范围。

管理界面位于「设置 → 通知策略」。运维事件支持 Telegram、邮件、Webhook 独立开关、定时维护静默及重复合并；原有管理员总开关、节点权限、用户通知开关和 Webhook 订阅过滤继续生效。

## 配置

常用界面只保留接收渠道、通知范围和允许故障恢复通知。通知范围提供「重要故障」「常规运维」「自定义」；事件与渠道的细分规则、重复窗口和维护窗口按需展开，不再默认展示事件×渠道开关矩阵。

「重要故障」包括节点/入站故障及恢复、配置下发失败、备份失败、证书续期失败和运行健康异常；「常规运维」覆盖除默认关闭事件外的全部运维事件。选择预设会明确替换细分事件规则，但保留接收渠道选择、恢复总开关和维护窗口。打开页面、折叠分组和暂停渠道不会自动重写已有自定义规则。节点、入站、插件的故障与恢复分组展示；组内支持关闭、仅故障、故障与恢复，并可展开细分渠道。旧配置的混合规则会显示「自定义规则」，直到管理员主动修改。

管理员会话通过 `GET /notifications/policy` 读取 `policy`、可配置 `events`、`channels` 和检查时间。`PUT /notifications/policy` 完整替换配置；没有填写的事件开关默认打开，`route_changed` 除外：该新事件按渠道默认关闭，需显式设为 true。重复窗口默认 300 秒。节点管理员、API 令牌和匿名访问不能调用新增接口。配置不开放通用 `/settings` 写入，避免绕过校验。

```json
{
  "repeatWindowSeconds": 600,
  "enabledChannels": {"telegram": true, "email": true, "webhook": true},
  "notifyRecovery": true,
  "channels": {
    "email": {"apply_failed": false},
    "telegram": {"backup_failed": true},
    "webhook": {"node_offline": true}
  },
  "maintenance": [
    {
      "id": "weekly-node-maintenance",
      "nodeIds": ["实际节点ID"],
      "channels": ["email", "telegram"],
      "startsAt": "2026-10-25T02:00:00+08:00",
      "endsAt": "2026-10-25T03:00:00+08:00"
    }
  ]
}
```

示例日期和节点 ID 需替换。时间必须为带时区的 RFC3339；按绝对时间比较，窗口开始时生效、结束时失效。节点列表留空表示全局，渠道列表留空表示三种渠道。指定节点的窗口不静默无节点归属的备份等全局事件。最多 20 个窗口，每个不超过 7 天，最多 100 个不同节点，引用的节点须存在；交叠窗口取并集。请求体最多 64 KiB，未知字段、未知渠道、不可配置事件及无效时间均拒绝，保存失败不改变旧配置。

`enabledChannels` 是本策略的运维渠道总开关，显式 false 暂停该渠道的全部运维事件，同时保留 `channels` 中的细分偏好；未填写的渠道保持旧行为。`notifyRecovery: false` 统一禁止运维恢复通知，包括 `health` 的结构化恢复消息，但仍关闭已记录的故障，避免下一次故障被错误去重。缺省或 true 允许按原细分规则发送恢复通知，不强制打开之前关闭的事件。这两层开关仅作用于运维通知，仍受 SMTP/Telegram 等原有配置与订阅限制；不会静默登录安全、客户或交易消息。

`maintenance: []` 清除所有维护窗口；`channels: {}` 恢复细分事件默认开关，不修改上述运维渠道和恢复总开关；`PUT {}` 恢复整个默认策略。策略作为一条设置原子保存，随备份恢复，多实例直接读取共享数据库，没有进程内缓存延迟。

## 事件范围

可配置事件如下：

| 事件 | 含义 | 合并方式 |
| --- | --- | --- |
| `node_offline` / `node_online` | 节点离线/恢复 | 故障与恢复配对 |
| `inbound_down` / `inbound_up` | 入站不可达/恢复 | 按独立入站配对 |
| `plugin_offline` / `plugin_online` | 插件不可达/恢复 | 按插件配对 |
| `health` | 均衡落地健康变化 | 使用结构化 `down` 值配对 |
| `apply_failed` | 节点配置下发失败 | 相同内容按时间窗口合并 |
| `backup_failed` | 定时备份失败 | 相同内容按时间窗口合并 |
| `cert_failed` | 证书续期失败 | 按证书和内容合并 |
| `node_traffic` | 服务器流量告警 | 按节点和内容合并 |
| `operational_alert` | 运行健康异常 | 按异常键和内容合并 |
| `route_changed` | 观察到检测路径变化（默认关闭） | 同目标/地址族在冷却窗口内合并所有变化 |

登录、封禁、恢复码、许可、升级结果、订单、工单、注册和客户流量/到期提醒不受此策略控制。携带用户 ID、用户专属消息、未知新事件，以及显式指定其他业务 Webhook 类型的事件都绕过运维降噪。`operational_alert` 的付款待交付、待人工对账和退款异常也绕过降噪，维护窗口不会吞掉这些消息。原有渠道总开关仍可关闭其原本负责的通知；此策略不会额外打开已关闭渠道。

## 合并语义

按渠道、接收人、事件组、节点和资源建立数据库状态。不同入站、插件、证书、管理员和 Webhook 互不占用合并记录。故障首次尝试发送后，同一持续故障不重复发送；已通知的故障恢复后尝试发送一次恢复消息，之后的新故障重新通知。没有通知过故障时不发送孤立的恢复消息。静默期间收到恢复仍关闭故障记录，防止恢复渠道后漏掉下一次故障。

除 `route_changed` 外，非配对事件在 `repeatWindowSeconds` 内合并相同内容；内容变化立即允许发送，例如新的下发版本或不同错误。设为 0 关闭这类时间窗口合并，不取消故障/恢复配对。下一条允许发送的通知附带合并数量，Webhook 同时包含 `notification_suppressed`；不修改其他渠道共用的原始事件内容。

维护期间的新通知丢弃，不积压，不在维护结束时重放旧事件；后续新事件重新按当前策略判断。若生产者只发状态变化事件，维护结束仍持续的故障不会凭空生成新通知，应查看节点、入站或运维健康页。已持久化、等待重试的运维 Webhook 则暂缓重试，每分钟重新判断策略；不消耗重试次数，恢复后沿用原事件 ID 和重试记录。既有业务 Webhook 仍正常重试。已经开始的网络请求无法撤回。

## 一致性与交付边界

数据库事务和行锁协调多实例，重启保留合并状态。记录的是发送尝试，不代表外部平台已确认送达。SMTP、Telegram 明确失败，或 Webhook 尚未成功写入持久交付表时，释放对应接收人的记录，允许后续同类事件重试；旧请求的失败不能撤销更新的记录。Webhook 网络失败继续使用原有持久重试机制。

本轮没有把 Telegram/SMTP 改造成可靠消息队列，也不承诺跨实例事件严格排序或网络投递恰好一次。进程在占用记录与外部发送之间退出仍可能漏发，网络超时后对方实际已收到也可能在重试时重复。数据库或策略异常时记录日志并放行告警；已读取到的静默策略在状态写入失败时仍生效。客户通知和安全事件不参与此状态机。

合并表只存资源摘要、发送令牌、状态、数量和时间，不存消息正文、邮箱、Telegram 聊天 ID或凭据；邮箱和接收人标识只参与摘要。节点删除会删除其合并记录；关闭的故障及非配对记录超过 30 天清理，未恢复故障保留。合并记录属于运行状态，不导入或导出到其他面板的备份；策略配置仍随备份保存。

## 验证

覆盖默认策略、严格配置校验、原子保存失败、管理员权限、维护时间边界、节点/渠道范围、故障/恢复配对、资源/接收人隔离、合并计数、明确失败后的重试及过期请求保护。使用模拟 SMTP、Telegram API 与 HTTP Webhook 实际验证三条发送路径，包括维护期间的 Webhook 重试和业务消息放行；共享数据库并发验证只有一次告警尝试胜出。

路径变化通知的开启方式、证据范围及冷却边界见[节点回程检测](node-route-trace.md)。该默认关闭事件在策略无法读取时停止投递；其他运维事件维持原有回退行为。


界面状态与表单逻辑验证：`cd web && node --experimental-strip-types --test scripts/notification-policy.test.mjs`（Node.js 22.6+）。覆盖旧策略识别、渠道关闭/重开、预设不意外启用渠道、默认关闭事件、自定义分组和未来事件保留。服务端测试额外覆盖三条运维渠道总开关、四类故障恢复、旧策略兼容和受保护通知放行。

## 到期与流量提醒的可靠投递

用户到期与流量阈值提醒在同一事务中保存提醒标记和各渠道的 `user_notices` 任务，不依赖内存事件队列。Telegram、邮件分别认领数据库租约并重试，指数退避最高 256 分钟；单实例最多四个发送并发，重复扫描不会叠加 worker。发送成功才记录 sent；已续期、流量重置、收件人变化或渠道关闭的旧任务记为 canceled。暂无可用发送配置时保留 pending。

身份、有效期/重置周期、提醒档位、渠道和收件人共同确定幂等任务 ID；正文和收件人加密保存，列表接口不返回它们。设置 → 通知策略中折叠展示最近 100 条发送结果。SMTP / Telegram 在远端成功但本地响应丢失时仍可能重复投递，不承诺严格一次送达。其他用户事件仍使用原有发送流程。旧版本已标记但实际漏发的历史记录不能自动判断或补发。

订阅 `user.expire_warn`、`user.traffic_warn` 的插件/Webhook 继续收到原有事件；对应 `webhook_deliveries` 也与提醒标记同事务提交，复用原有签名与重试机制，不经过内存通知队列。
